New findings

  • Known-email overwrite (source-read only). SubmissionModel::createLeadFromSubmit (sha256 041db937…) matches a submitted email to an existing contact and writes non-blank fields to it. The "contact 1 unchanged" proof only covers cookie-based association, not a submission that uses contact 1's email. Excerpts are in logs/native-source-review.txt.
  • 10 unit survivors, none of them a bypass today: the POST status/errorMessage/validationErrors checks, email format, firstname control characters, the read method check, HEAD returning an empty body, exact form Content-Type, the Content-Length precheck (the stream cap still covers it) and the CSP header (the replay asserts CSP on the real edges). See logs/mutations-r2-extra.json.
  • The DNT fix depends on Mautic's code. IpLookupHelper::isRequestTrackable (sha256 ddf67f36…) honors DNT/Sec-GPC with no config switch. It is safe on the pinned image, but the readcheck must be rerun after any Mautic upgrade.
  • Network scope. public-a shares its tenant network with db-a, bridge, mime-sink and authority. It holds no credentials for any of them.

Not verified (full P2 stays open)

Browser rendering and CSP enforcement; DNS/TLS/LIVE; rate limiting and abuse control (the static token can be replayed); slow clients and connection exhaustion; callback binding; dynamic publish/unpublish; duplicate or lost-response recovery (a 502 after native success can cause a duplicate on retry); native JS forms, uploads, conditional fields, captcha and native actions; the known-email overwrite at runtime.

What I did not do

No source edits, setup, fixtures, restarts, deletes, worker or mail. I did not rerun the old host baseline or unmarked native GETs. Read-effects and replay each ran exactly once. The only new native rows are the one synthetic contact and submission per tenant from the replay. Machine-readable results are in verdict.json.
