Replay and limits

With the already initialized isolated services running: pnpm --dir proofs/marketing test and pnpm --dir proofs/marketing typecheck. The test command verifies image/source/network identity, installs the current plugin, then runs approval/revocation/crash, native open branch, re-entry and ordinary API refusal checks. Run pnpm --dir proofs/marketing proof:reliability for late approval, refused/busy sink, real lost socket response with bridge restart, and simultaneous Doctrine workers against a duplicated synthetic queue item. It creates new synthetic fixtures and retains old records. Complete replay output; typecheck output.

Initial bootstrap uses setup.mjs, loopback SSH forwarding into the existing local VM, initialize.mjs, configure.mjs, a native fixture, bridge setup and enable-guard.mjs. That transition retains the stopped null-transport baseline container. The initial native-hook-replay.mjs belongs to the capture-only stage before enabling the guard; the complete test command is the current replay path. No global Docker context/network changes or additional large image pulls are needed. Paperclip is untouched.

The bridge is deliberately bounded to 128 intents, one concurrent request, one recipient, one fixed synthetic instance/contact mapping and no attachments. SQLite stores consumed intent state before delivery; a crash cannot mint a new attempt for that occurrence. Synthetic delivery receipt and delivered intent state now commit in one SQLite transaction. Only an already-delivered receipt may be replayed to reconcile H0 and acknowledge the queue without a new effect. The one-second Doctrine redelivery timeout is a test override to exercise actual queue redelivery. Missing, refused or uncertain authority closes delivery. A never-claimed proposed intent stays sealed for a later approved worker retry. This only covers approval while Messenger retry remains available; eventual dead-letter exhaustion still needs operational requeue and campaign approval integration. Consumed intents without receipts remain held; operational recovery of those holds is not implemented.

Accounting has three distinct outcomes. (1) Worker killed after consume, before sink: zero receipts, H0 outcomeUnknown, bridge consumed, no transport acceptance. Mautic's native campaign log can still be triggered. (2) Sink commits its synthetic receipt then loses its response: the worker throws, a later retry uses only that durable receipt to reconcile and acknowledge; one effect and one H0 receipt. (3) Sink refuses before any effect: worker throws, zero accepted events/receipts, consumed hold remains unknown. Definite busy503 alone permits at most three attempts within the same call. These receipts belong to the bridge itself, not an independent mail sink. Mautic queue/campaign/email_stats counters or tracking pixels do not establish delivery; real SMTP, headers, inbox placement, complaints and provider behavior were not exercised.
