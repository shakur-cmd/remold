Done and proven (builder-run only)

  • Each tenant's worker runs in its own Docker sandbox with no network, only its own workspace volume, a read-only root, a non-root user and no secrets in its environment. Tenant A cannot see tenant B's files or reach B's service, the host, the internet or a metadata address. Tenant B cannot see A's either.
  • A missing executor cap means zero. The run is refused before anything is reserved.
  • 36 runs were launched in three concurrent waves, each asking for 4 units. Final spend stayed within the caps: tenant A 8 and B 4 against 10 each, 12 against the shared 15. No reservation leaked. At most one sandbox per tenant was dispatching at a time. Every run reports its full reservation as usage, so any over-reservation would have shown up as over-spend. Reserved amounts were not sampled mid-flight.
  • The org kill switch stopped a running sandbox 159 ms after it was set. The stated bound is 1,500 ms. Queued work for that org was refused, and the other tenant's run finished normally.
  • Cancelling one run stopped its sandbox in 99 ms. The executor-wide (global) kill stopped both tenants' sandboxes in 63 and 66 ms and refused new runs.
  • A result that came back after a cancel was recorded as late and billed, but its output was not applied. The same holds for a result that came back after the org kill switch. A replayed result with the wrong fence was refused.
  • A run with no usage report was not applied. It put the tenant into the H0 "usage unresolved" hold, which blocked that tenant's next run and left the other tenant working.
  • A model that ignored its token limit was stopped and marked as an overrun, and its tenant was held. A hung model was stopped at its 800 ms duration limit.
  • All 16 deliberate breakages ("mutants", one per guard) made their named check fail. The suite passed on the final run and in three repeat runs.

How it works

The trusted executor runs on the host and holds the adapter and agent session tokens. The sandbox never sees them. Each run starts a warm sandbox first. Only then does the executor call H0 in order: claim (atomic reservation), permit, consume. It hands the stub model its token limit over stdin, reads the streamed tokens and reports with reconcile.

The sandbox has no network at all. Stdio to the executor is its only channel, so every model or tool call has to go through Remold's capability path. While a run is live, a watcher reads adapterStatus every 100 ms. It kills the sandbox on cancel, org kill, grant revocation or lease expiry. It also kills when the global hosted flag is off, the token count passes the permit, or the duration runs out.

Output is applied only when all of these hold: the run was not killed, the model reported usage, no cancel or kill showed up before reconcile, and reconcile came back accepted, not late and not overrun. A killed run is billed from the executor's own token meter.

Stated kill bound: 1,500 ms from trigger to sandbox exit. That is the 100 ms watch interval, plus one status read, plus docker kill. Measured: 159 ms (org), 99 ms (cancel), 63 and 66 ms (global).

H0 gaps found (for root, Fable and Opus)

  • The org kill does not mark in-flight results late. reconcile ignores readonly, so a result that lands after the org kill is recorded late: false. The executor covers this by checking status just before reconcile. A kill that lands between that check and reconcile would still slip through. The durable fix is for the CRM write that applies the output to check readonly atomically, as applyChange does, or for H0 to treat readonly as late.
  • Leases cannot be renewed. The H0 lease is 2 s from claim, and adapterStatus reports cancel once it expires. So any hosted run longer than about 2 s is killed. That is fine for the stub but not for real agent turns. It needs a fenced lease renewal.
  • Overshoot past the reservation is possible. A model that ignores its limit can produce more before the kill lands. In the test it billed 9 units against a reservation of 4, within 64 ms. H0 flags it as an overrun and holds the org, so no new spend follows. The per-run hard cap is therefore "reservation plus whatever arrives within the kill bound". Real providers need their own max-tokens limit enforced as well.
  • The global kill is executor-local (one host). A kill across several hosts needs a control-plane flag. H0 has only the per-org readonly.

What stays open in P6

  • Real hosted executor. This is a local proof harness on the colima-remold-proof VM, not a deployed service.
  • OS-level isolation on the real host. Docker on a shared Linux kernel here. There is no gVisor or Firecracker boundary and no hostile escape testing. Egress policy, resource exhaustion across tenants and container-escape tests on the real host are all unproven.
  • Real-model smoke and real usage reconciliation. The stub reports usage itself. Provider-origin usage, active stream cancellation with real billing, and step or tool-call limits from real agents are unproven. Real tools are not wired, and delegated descendants are not revoked here (that is H0 and P1 territory).
  • Subscription route. Still only the owner-local CLI feasibility in proofs/runtime/report.html. No customer execution on Shakur's subscription.
  • Funding gate. Unchanged. Live funding method, provider terms and a numeric spend cap are required. The default is zero.
