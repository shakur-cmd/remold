Defects with repro

Defect 1 - org-kill reconcile-window race (builder-disclosed, confirmed reachable)

executor.mjs:110-116 computes cancelled from a final status read, then reconciles, then applies output when !cancelled && !late. The H0 reconcile computes late = revoked || cancelled(cancelRequestedAt) || absence || released || op.late - an org set readonly is none of these, so late stays false. Setting readonly after the final check but before reconcile lets the output apply.

Repro: attack test "widened org-kill race", 8 iterations, hook sets control{readonly:true} in beforeReconcile. Result: applied 8/8, each with late:false, org spent 4 each. See attack-results.json.

Defect 2 - usage is self-reported by the tenant guest for finished runs

executor.mjs:107: const usage = box.killed ? box.tokens : box.done?.usage. The executor keeps its own token meter (box.tokens) and uses it for killed runs, but for a finished run it trusts the number the guest wrote on stdout. A hostile guest can under-report (consume more than it pays for) or over-report.

Repro: attack "guest-controlled usage report". Under-report: streamed 4 tokens, reported usage 1, billed 1, applied. Over-report: reported 999, billed 999 past the org cap of 10, which trips the usageOverrun anomaly and is not applied (so over-reporting is self-limited, under-reporting is not). Forged-id run also billed its own org 999999 the same way. See attack-results.json.

Why it matters: the slice does not prove tamper-proof usage. In a real hosted executor, usage must come from the trusted model runtime, not the tenant process. As a stub this is acceptable to demonstrate the control plane, but the claim "usage reported" should be read as "the control plane books whatever usage the executor hands it", not "usage cannot be lied about".

Also confirmed from the builder's own disclosed gaps

  • Non-renewable 2 s lease: confirmed. Any run whose work exceeds ~2 s after claim is cancelled by lease expiry regardless of intent; my first hostile probe was killed this way until I made it finish inside the lease.
  • Spend overshoot before kill: confirmed. Overshoot mode billed 9 units against a 4-unit reservation before the token kill landed; over-reporting bills past the cap before the anomaly hold engages.
  • Global kill per host only: not contradicted, not independently testable on a single host. Accept as disclosed.

I1 production cross-check (read-only, no changes)

The certified I1 code merged at 328941c has the same org-kill-not-late shape at convex/integrations/outcomes.ts:36: const cancelled = op.cancelRequestedAt !== undefined, late = revoked || cancelled || !!op.absence || op.released || op.late; - readonly is not a late trigger, identical to H0.

Reachable as: an accounting/audit misclassification. A permit already consumed before the org goes readonly will reconcile with late:false and emit a confirmed event rather than a completedAfterCancellation-style event, and it books the spend.

Not reachable as: a write bypass. Unlike the P6 executor, nothing in I1 applies provider output to domain records gated on the reconcile late flag (grep for consumers of .late and any apply-output path found none). Every domain write goes through writable() - core.ts:70 inside checked(), and commands.ts/bindings.ts/connections.ts import it directly - which throws on readonly. The permit path (dispatch.ts:8) and the status query both call checked(), so a readonly org is denied new permits and its in-flight op is signalled to cancel. So the same line should be fixed for correctness of the audit trail, but it is materially less severe in I1 than in the P6 stub executor, where the executor itself is the thing that applies output on !late.
