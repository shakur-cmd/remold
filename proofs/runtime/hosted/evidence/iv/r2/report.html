Racing settle.ts itself

The apply cannot be split. In Convex a mutation is one serializable transaction, and settle reads adapterStatus and writes the output record inside it, so a kill cannot land between the status read and the write: it commits before settle's snapshot (settle sees cancel) or after settle commits. I stressed this two ways - readonly at 0-4 ms before settle over 50 trials, and readonly fired unawaited to race the transaction over 40 trials - and never saw a phantom apply, a double apply, or a spend that was not exactly the meter. The global kill has one honest semantic worth stating plainly: disable() sets the in-memory flag and the executor reads it synchronously right before sending settle, so a kill that arrives after that send does not recall the already-dispatched apply - disable() instead waits for it. That is correct kill-switch behaviour (a committed transaction cannot be un-committed), not a leak; a kill before the send blocks the apply, which the probe confirms.
