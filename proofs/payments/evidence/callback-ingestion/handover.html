P4 durable callback ingestion, local SERVICE/SIM proof

2026-09-26 · scope: remold/P4/callback-ingestion · evidence level: SERVICE/SIM, builder-run · status: awaiting independent verification

Your calls

  • Events for a connected account we have not bound are now refused (HTTP 400), so the provider retries them. The alternative is to accept and park them. Refusing means an account that stays unbound for days will show as failing deliveries on the provider dashboard. I chose refuse; say if you want parking instead.

Done and proven (builder run only)

  • This is a builder-run SERVICE/SIM proof. Nobody independent has checked it yet. Actual provider ingestion (real Stripe deliveries into a durable endpoint) remains open.
  • No Stripe API calls, no sandbox writes, no provider activity. The signing secret is synthetic and random per run. Provider state is an in-process stub. Spent sandbox latches and private journals were not touched.
  • Before: the existing code passed 5 of 6 cases and failed substitution. It acknowledged events for unbound or missing accounts with 200 and dropped them, and a refused event stopped the reconciliation loop, leaving the receipt stuck.
  • After: 6 of 6 cases pass. Each case produces exactly one durable receipt and one reconciliation, or a refusal, bound to the claimed merchant.
  • Mutations: removing the dedupe key, the signature check, or the account binding each makes at least one case fail.
  • None of the 54 frozen payment source files changed. Typecheck passes.

What was built

The existing pieces stay as they were: verifyStripe in webhooks.mjs, the Convex ingest, pendingEvents and ackEvent functions and the payIncoming table, and the account-scoped pull in adapter.mjs. The work added three files around them.

FileWhat it does
proofs/payments/callback-ingestion.mjsReceiver: verify the signature, bind the event to exactly one merchant by its claimed connected account, store the receipt, and only then return 200. It refuses unbound or missing accounts. Drain loop: for each pending receipt, run a fresh account-scoped provider read, then acknowledge. Final refusals are recorded and closed. Transient errors stay pending, and one bad receipt no longer blocks the rest.

Findings to know about

  • A crash after the ledger write but before the ack is an extra probe, not a required case. It causes one more idempotent provider read after restart. The ledger is unchanged and the receipt drains once, but a second payment.observed audit row is written. This happens both before and after the change. Removing it would need the ack and the ledger write in one transaction.
  • The substituted event claiming B leaves one closed receipt and one refusal event on B, because it names B. B's financial export (quotes and documents) never changed.
  • The fixture covers one-time invoice events only. Renewal invoices created by the provider (the observeRenewal path) are not routed by this drain and would be refused as unbound.
  • Tenant B had no events of its own, so the account mutant was caught by the substitution case, not by the B check.
