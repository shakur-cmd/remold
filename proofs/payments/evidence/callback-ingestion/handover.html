Why R2-4 now fails

R2-4 queues a 401 receipt and then a 429 receipt, and drains once. The 401 now pauses reading for every merchant (fix 1), as the coordinator asked. So the 429 receipt is not read in that pass. It stays open, which is correct, but R2-4 expects a retry outcome in that same drain. My check 11 covers 429 on its own: it is deferred as provider_429 and the receipt stays open. R2-3 confirms 429 is classified as retryable.

Things to know (round 3)

  • During a pause, each drain makes one probe read per paused scope. That read is how the drain notices recovery.
  • The sweep's stale query filters the binding's documents in externalId order. It reads a bounded batch, but a binding with very many complete invoices ahead of the incomplete ones would make that scan longer. A production version should add an index on the incomplete flag.
  • The sweep and the drain are separate calls. A hosted schedule has to run both, and none exists yet.
  • The frozen ackEvent does not remove schedule rows. admit removes rows whose receipt is closed, up to 200 per drain.

What each fix does

#Problem found by the verifierFix
1One merchant with revoked access stopped the drain for every merchant after it.drain() catches failures per merchant and per receipt. A failing merchant is reported as merchant_error and the rest carry on.
2Only the stub's error text counted as final. A real provider 404 retried forever, and 100 stuck receipts hid every newer one. The receipts query threw above 100 rows.Classification uses the error's type and fields, not its text. A StripeFailure with a 4xx status other than 408, 409 or 429 is final. So is a node:assert failure such as "Live response refused". Anything else can be retried: it backs off exponentially and is skipped until due. After 5 attempts it is closed as failed with a payment.callback.failed audit row. The due query skips receipts that are waiting, so they cannot hide newer ones. The receipts query returns the newest rows, or one event's rows, and never throws on volume.
3Refusals were found by matching Convex error text, which production Convex hides.A typed prepare query decides before any provider read and returns {action:'refuse', code}. The new Convex functions throw ConvexError({code}). Every run of the suite now hides error text the way production does (callback/redact-hook.mjs).
4charge.refunded, charge.dispute.created, credit_note.created and customer.subscription.* were accepted and then closed silently as "unbound".Refused explicitly with code unsupported_event_type and an audit row. I did not choose the re-read route. The existing adapter can only re-read by invoice id. Mapping a charge, dispute or subscription to its invoice would need provider read paths nobody has tested against real shapes. The invoice's own events and pulls still pick up refunds and credit notes.
5Coordinator decision: unbound accounts should not get 400.A signed event for a well-formed account with no binding gets 200. It is parked in callbackParked, keyed by (account, event id) and capped at 500 rows. A per-account alert row in callbackAlerts counts arrivals, and overflow gets its own alert kind. Nothing reads parked rows back as effects. Parking needs an ingress token, and it refuses an account that is actually bound. A missing or malformed account, a bad signature or a malformed body still gets 400.

Things to know

  • The new tables are added the way recurring/ does it. callback/schema.ts imports the frozen payment schema unchanged and adds four tables, and the runtime copy uses it. A real deployment would need the same additive schema change reviewed.
  • A node:assert failure counts as final. That includes a traversal race such as "Invoice changed during traversal". The receipt closes, and the document stays marked incomplete until the next event or pull. That is safe, but it is not a retry.
  • Plain errors from the frozen payment mutations (currency or total mismatch) are hidden in production. So they are retried and then closed as failed after 5 attempts, not refused on the first try.
  • A backlog of more than 1000 receipts all waiting at once could still delay newer ones, because the due query scans at most 1000 open receipts. The 5-attempt limit means that delay ends.
  • The ack-loss probe is unchanged. One extra read after restart writes a second payment.observed row. The ledger is unchanged.
  • Not rerun against the new code: the verifier's own 6 mutants. Their anchors target round 1 text. My 11 mutants cover the new guards.
