Does any path still close a receipt that a later recovery could have completed?

  • Closed after a provider read (attempt cap on 5xx or network errors, a final 4xx, or an assertion failure): yes, the receipt closes. But the invoice was already flagged incomplete before the read, and the sweep completes it after recovery (R3-10, R3-11). The effect is recovered; only the trigger is lost.
  • 401/403: never closed (R2-4b, R3-1, R3-2, R3-3).
  • Refused before any read, with unbound_document, when an event arrives before attachProvider has recorded the invoice id (R3-12, observation). The invoice is not flagged, so the sweep never sees it. In the current flow that event can only be invoice.created or invoice.finalized during the adapter's own create call. The adapter reconciles itself right after, so there is no money gap. It is worth knowing if invoices are ever created outside the adapter.
  • Refused with unsupported_event_type (refunds, disputes, credit notes, subscriptions): closed without a re-read. The builder disclosed this and it is outside this slice.

Observations (no defect at this level)

  • Concurrent drains spend attempts. In R3-8, drains running in parallel made 198 receipts back off with retryable_error (stale adjustment generation), all later applied. Run the drain one at a time.
  • The clock is supplied by the caller. Forward jumps can use up all 5 attempts within seconds (R3-10: attempts 1 to 5 across five jumps, then closed). The sweep repairs this. A hosted schedule must pass a real clock.
  • The sweep scans without an index on the incomplete flag. The builder disclosed this. With very many complete invoices per binding, the scan could hit Convex read limits and turn into a merchant_error for that merchant's sweep. Not tested at that volume.
  • An alert only resolves on a successful read. In every case I tested, the paused receipts remain due, so the next drain probes and resolves it.

Test corrections I made during this round

  • R3-3 (first run): after recovery there were no due receipts, so a later 401 had nothing to probe and correctly opened no new episode. I changed the test to deliver a receipt before each drain.
  • R3-6 (first run): the check counted a failed row from R2-5 that was written earlier in the same run. I changed it to count only new rows.
  • R3-8 (first run): 98 receipts were still open, because they were backing off after the concurrent-drain stale-generation retries; none were stranded. I added a diagnostic (scheduled, stranded, codes) and quiesced with advancing clocks. The unedited first-run logs were overwritten; the diagnosis is recorded here.
  • The run was reorganised so that attacks/watermark-stall.json comes from the --scan run, where R2-11 catches that mutant.
