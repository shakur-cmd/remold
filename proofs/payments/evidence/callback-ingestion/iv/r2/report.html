Your calls

  • Should 401 (and 403) from the provider close a receipt forever? Today they do. An expired or rotated platform key closes every due receipt of every merchant in one drain pass. I recommend retrying 401 and 403 as merchant or platform conditions, and stopping the drain for that merchant, instead of refusing the event.
  • Is 7.5 minutes long enough before a receipt is closed as failed? The backoff is 30, 60, 120 and 240 seconds, and the 5th attempt closes the receipt. The provider already got a 200, so it will not redeliver. A provider API outage longer than about 7.5 minutes loses the trigger for every event received in that window. The document stays marked incomplete, so money is safe, but nothing re-reads it until another event or a pull. I recommend a longer cap (hours) or a sweep that re-reads incomplete documents.

Defects (new in round 2)

1. 401 and 403 are treated as final, so a credential problem closes every due receipt (medium, liveness only). classify() treats every 4xx other than 408, 409 and 429 as final. A 401 means the platform key is invalid, expired or rotated; a 403 means a permission problem such as a revoked Connect account. Neither is a property of the event. Repro R2-4b: a stub returning new StripeFailure(401,…) for a bound invoice gives outcome refused provider_401, the receipt is closed, and there is an audit row. The provider will not redeliver because it already got a 200. Money is safe because the document stays incomplete, but the trigger is lost.

2. The 1000-row scan still starves newer receipts behind a large backlog (low, disclosed by the builder). Repro R2-11: 1001 receipts failing with 503. Ten drains defer 1000 of them. The 1001st row and a newer valid receipt sit beyond the scan limit. The newer receipt is not applied at the same clock, and still not after 30 drains at the next backoff time, because the first 1000 rows are re-deferred before the scan reaches it. By reading the code, the starvation ends only when those 1000 close as failed (about 7.5 minutes of clock). That fits the builder's disclosure, but "newer receipts are not starved" holds only below 1000 open receipts per merchant.

3. classify() throws on a non-Error thrown value (low). 'requestId' in error throws a TypeError for a thrown string or number (R2-3c). In drain() the inner catch calls classify, so the outer catch records item_error. The receipt stays open with no attempt counting and no backoff, so it is retried on every drain. The current adapter only throws Error objects, so this is latent.

Observations

  • A parked duplicate with a different body is accepted silently as a duplicate, with no digest comparison. It has no effect because parked rows are never applied.
  • The parked query shows at most 100 alert rows and the alerts table is not capped. The number of alert rows is bounded by the number of distinct connected accounts on the platform.
  • Ack-loss duplicate audit row: the probe is unchanged. The ledger is equal to a clean drain, and the duplicate row stays harmless.
  • The builder's backoffMs:0 wiring for my attack 10 is legitimate. I tested real 30s backoff separately in R2-5.
