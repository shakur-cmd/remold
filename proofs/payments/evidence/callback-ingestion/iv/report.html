Your calls

  • Unbound connected account: refuse (400) or accept and park? My recommendation is accept and park with no effect. The drain always re-reads the provider, so the event body carries nothing we need later, and binding a merchant should start its own full pull anyway. A 400 turns one unbound account into a failing endpoint on the provider dashboard, which (by my understanding of Stripe's policy, not checked in this session) can lead to warning emails and endpoint disabling that would hit every merchant. Keep 400 for bad signatures only.
  • Should the three drain defects below be fixed before this slice counts as integrated? I recommend yes. They are about the drain getting stuck, not about money going wrong, but defect 3 means substitution refusals would never close on a production Convex deployment.

Defects

1. One failing merchant stops the drain for every merchant after it. In callback-ingestion.mjs drain(), await pending(merchant) sits outside the try block, and so does refuse() inside the catch. If a merchant's adapter access is denied (disconnected, revoked or restricted), the whole drain throws. Repro is attack 12: merchants [A with a revoked token, B], with a valid pending receipt on B. The drain throws "adapter account denied" and B's receipt stays pending. Fix: a try block around each merchant.

2. A receipt that keeps failing with a non-matching error is retried forever, and 100 of them starve the binding. FINAL matches No such object, but that text only comes from the replay stub. The real client (stripe.mjs StripeFailure) says Stripe sandbox request failed: 404 invalid_request_error resource_missing id. Non-sandbox does not match the real client's Live response refused either. pendingEvents takes 100 per binding in creation order, so 100 stuck rows hide every newer receipt. Repro is attack 13: a bound document whose provider object returns a StripeFailure 404, then 100 events for it (all "retry"), then one valid event for another invoice. That valid event is never picked up across two further drains. Also, callbackIngestion.receipts throws "receipt bound reached" once a binding has more than 100 receipts in total, so the measurement query stops working.

3. Classifying refusals by matching error text will not work on a production Convex deployment (not reproduced here). Convex docs (docs.convex.dev/functions/error-handling) say that in production, server errors that are not ConvexError are cut down to the function name and a generic "Server Error". So unbound provider document would never reach the drain. Substituted and foreign-invoice receipts would retry forever and feed defect 2. Local dev deployments show the full message, which is why the builder's run passes. Fix: throw ConvexError with a code, or have observe return a typed refusal.

Observations (not defects in the claims)

  • The duplicate audit row after an ack loss is harmless. After a crash between the ledger write and the ack, the document is field-for-field equal to a clean drain, apart from the adjustmentEpoch counter (7 vs 8, which moves on every read). The extra payment.observed row records a real second provider read. Nothing in the repo counts payment.observed except the replay fixture.
  • Refund and dispute notifications are accepted and then closed. A charge.refunded event for bound B (charge id, not invoice id) got a 200, and the drain then refused it as "unbound provider document" and closed it with 0 observations. So those notifications do not trigger a re-read of their invoice. webhooks.mjs subscribes to charge.refunded, charge.dispute.created, credit_note.created and customer.subscription.*. The builder disclosed that only one-time invoice events are covered. This is bigger than renewals alone.
  • Signature window is 300 seconds each way. t-295 and t+295 are accepted. t-305 and t+305 are refused. A header with one wrong v1 and one right v1 is accepted, which matches Stripe's multi-signature scheme. v0 only, an empty header, and an HMAC without the timestamp prefix are all refused.
  • verifyStripe refuses livemode:true, so this receiver is sandbox-only as frozen. A live route needs a separate, reviewed change.
