PLAN: own CRM on Convex

Revision: r3, 2026-09-22. Name: Remold (filled 2026-09-22 after approval, domain remoldcrm.com). Author: Fable 5.1 (this session). Challenger: Astra (gpt-6-astra).
Assumptions ledger: grill-ledger.md (settled, not re-asked). Source prompt: 2026-09-22-crm-build-prompt.md (constitution, superseded where this plan differs).

Goal

User: Shakur, running CodeMyVibe's outreach, client projects, and delivery, working with AI agents on a Mac Mini and an HP laptop. Later: small service businesses whose work is not "contacts and deals".

Problem: EspoCRM on the HP sandbox holds the outreach funnel today. Agents reach it through a script, data lives on one machine, nothing updates live, and every extension is PHP. Nothing lets an agent act as a team member with attributable, reviewable changes.

Observable end result: Shakur's outreach and client projects run in a CRM he built. Mac, HP, and phone show the same record within two seconds of any change. His Claude Code or Codex session, on his existing subscription, creates and updates records through MCP with every change attributed to that agent and reviewable before it lands. Custom objects (Community, Lead, Project) work exactly like Person and Company. Public AGPL repo a stranger can run.

Switch-over line (from ledger): Steps 0 through 5 plus Step 6 (import and rules-based dedupe). Step 7 (decide and Jev) onward comes after Shakur lives in it.

Locked constraints (source: grill-ledger.md unless noted)

  • Convex for all data, functions, storage, scheduling, search. Convex Cloud free tier for the build; self-host proven once at Step 13.
  • No LLM key or provider adapter in the CRM. LLM work happens in the user's subscription session over local stdio MCP or REST. Jev is the only server-side model, org key, via decide() with rules fallback and a decision log.
  • Clerk for identity behind one identity module. Orgs, members, roles, invites, agent keys live in Convex.
  • AGPL-3.0. Public repo from first commit at github.com/shakur-cmd/remold. From scratch; Twenty is a design reference, no copied code.
  • Stack: Vite, React, TypeScript strict, React Router, Tailwind, shadcn/ui, TanStack Table, dnd-kit, pnpm, vitest with convex-test.
  • Convex limits (verified 2026-09-22, docs.convex.dev/production/state/limits): 32,000 documents scanned and 16 MiB read per function, 1 MiB per document, 4,096 index ranges read. The source prompt's 8k / 8 MiB is stale.
  • Metadata first: standard objects are seeded metadata; a feature that only works for seeded objects is not done.
  • Suggest then apply: agents propose by default; auto-apply is granted per agent per action type.
  • Every write goes through applyChange, which validates against field metadata and appends an events row.

Exclusions (not in this plan)

Products and quotes, multi-currency, marketing forms and landing pages, mobile app, SSO, billing, remote MCP with OAuth (named as a later step but not specified here).

Verification roles

  • Builder: the session that writes the code (Claude Code or Codex). Records evidence, never certifies.
  • Independent verifier (IV): a fresh Fable or Astra session with repo access and no build context. Repeats the check from the plan text alone.
  • Shakur: only for checks that need his accounts (Clerk dashboard, Convex dashboard, TypeSafe key, Gmail) or his judgment. Each such check names what he must do in one line.

Step 0: Records design decided with a benchmark

Outcome: Every later step can trust that a list of 50k records on a custom object opens fast. Shakur avoids a rewrite after month three.

Build: docs/adr/001-records.md comparing at least: (a) one records table with typed indexed slot columns mapped from field metadata; (b) records plus per-field recordValues rows indexed on (orgId, fieldId, value); (c) schema regeneration per org. A throwaway branch implements the two viable options enough to benchmark. Also docs/adr/002-events.md: the events row shape and applyChange signature.

Prove it: Starting state: exactly 50,000 records seeded deterministically (fixed RNG seed) on a custom object with 12 fields, including custom number field score (uniform 0 to 9,999) and custom select field stage with 5 values at 40/30/15/10/5 percent, on a Convex Cloud dev deployment. The seed script also writes bench/expected.json: the first 50 record IDs for each query computed in plain TypeScript from the fixture, independent of Convex. User action: run pnpm bench three times, page size 50, 20 samples per query per run. Sort order is always the named field then _creationTime desc then _id as tie-breakers, applied identically in the fixture computation and the query. Queries: (1) first page sorted by score desc; (2) stage equals the 5 percent value; (3) stage equals the 30 percent value sorted by created time desc; (4) page 2 of query 1 by cursor. Expected: returned IDs and order equal expected.json for every query; p50 under 100 ms and p95 under 250 ms server-side; each query reads under 4,096 index ranges and 32,000 documents (asserted). Pass: correctness and timing met on all three runs for the chosen option. Fail: any wrong or missing ID, any timing miss, or any query that scans. Recovery case: insert record 50,001 with score 10,000, strictly above every seeded value; query 1 now returns it first and timings still pass.

Evidence and verifier: bench/results-<date>.json with raw timings and Convex function log excerpts showing read counts. IV runs pnpm bench on a fresh clone against the same deployment and matches numbers within 20 percent. PENDING.

Expected: pnpm import:reconcile <source-dir> reports every source ID present exactly once, every mapped field equal after normalization, every relation resolved to the record with the matching source ID, zero extras. Private run: same reconcile against the EspoCRM export, then Shakur freezes EspoCRM, exports again, and a delta import plus reconcile shows zero differences. Pass: reconcile reports zero mismatches in both runs, including after the interrupted-and-resumed public run. Fail: any missing, duplicated, or mislinked record. Step 8: Shakur automates without code, and formulas update live

Outcome: "When a Lead becomes Won, create an onboarding Project with its Tasks" runs on its own. A formula field shows days since last touch and recomputes live.

Build: Automations: triggers (created, updated, field changed, time based), conditions in a sandboxed expression language evaluated in a Convex function with a step and time budget (never eval), actions (update field, create record, notify, call webhook, add to agentInbox, ask decide()). Formula fields using the same expression language. Every automation run carries a chain depth (events written by an automation carry depth + 1) with a hard limit of 5, and an idempotency key (automationId, triggeringEventId) so a retried run never executes its actions twice.

Prove it: Starting state: seeded org. Actions: build the Won automation in the UI; add formula field daysSinceTouch on Lead; move a Lead to Won. Expected: the Project and its three Tasks appear within 5 seconds, audit actor is automation:<id>, and the formula on another Lead changes when its last-touch date is edited, live in a second browser. Pass: observed on Lead and repeated on Job with a different trigger. Fail: automation runs twice for one change, or a formula with an infinite loop hangs a function. Failure cases: (1) an expression that exceeds the step budget is rejected at save with a message; (2) two automations that trigger each other (A sets field x, B sets field y on x change, A on y change) stop at depth 5 with a visible "chain limit reached" run record and the org stays responsive; (3) with test flag AUTOMATION_FAIL_AFTER_ACTION=2, the Won automation fails after creating the Project and one Task, the run shows failed, retry completes it, and reconcile shows exactly one Project and three Tasks; (4) a runtime error in an action is logged and does not block the user's write.

Evidence and verifier: recording, events rows for the automation, vitest for the expression budget. IV builds a different automation on Job. PENDING.
