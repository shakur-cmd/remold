What Baserow was doing for us

Five jobs, from most to least important. Most of them had already stopped running.

  1. Website leads. Every form, chat and preview claim became a row with a dedupe key, status "new", contact details, what they want, consent and source. Now emailed.
  2. A timeline per client or prospect. Events like scan, view, claim, reply, call and booking, each with a time and a source. Desk notes were added to it too.
  3. Prospect pipeline. One deduped row per prospect, with a status that only moved forward (discovered, approved, mailing, delivered, viewed, contacted, call booked, won, lost and so on). Fields you own, like outcome notes, were never overwritten by automation.
  4. Outcomes and numbers. Won or lost, with a dollar value. Those fed the funnel rates: scan to call, and call to won.
  5. Bulk prospect import. Deduped on name, domain, email, phone and address, checked against a do-not-contact list, with a record of each import run.

What Remold must do, and what it has today

Remold already has a REST API with per-key permissions, list and filter, record history and CSV import. The gaps are below, in the order they matter.

#Remold mustTodayWhy it matters
1Ignore a repeated request. An Idempotency-Key on POST /api/v1/changes so a retried form or webhook makes one record, not two.Missing (designed in ADR 002, not built)Forms retry, and so do webhooks. Without this, leads are duplicated.
2Find or create a person by email or phone in one call, so the same person is never added twice.Missing (two calls, not atomic)The same owner fills the form twice, or chats and then books.
3Store lead details on a Person or Opportunity: source, ref or UTM, what they're launching, when, consent, and the full message.Partial: custom fields exist, but only 8 text fields per object can be filteredYou need to see where each lead came from, and to filter by it.
4Log events on a record (scan, view, claim, reply, call, booking, note), each with type, source and a full timestamp.Partial: notes work, but date fields drop the time of dayThe timeline is how you know who is warm.
5Fields automation can't overwrite, such as outcome and your notes, and a status that only moves forward unless a person changes it.Partial: capability grants can be scoped to fields, with no UI and no forward-only ruleAgents must never undo your calls.
6Import with dedupe on email, phone, domain and normalized name, plus a do-not-contact list that every import checks.Partial: CSV import dedupes on the title (name) onlyProspect lists are only worth it when they're clean.
7Filter on more than one field, and by date range, e.g. events of type "booking" in September.Partial: one exact-match filterThis is how you get the funnel numbers.
8Notify you about new leads by email, or through an outbound webhook that something else turns into an email.Missing (planned as job I9)Not urgent, since the website emails you already. Needed once leads come from places other than the website.
9Accept third-party webhooks (tawk.to, Cal.com, Stripe), with signature checks.MissingLow priority. A small function in between can call the REST API instead.

Smallest useful first step

Build items 1 and 2, then add these fields on Opportunity: source, ref, launch kind, launch month, details. With that, functions/api/intake.js on the website can keep emailing you and also make one Remold call: find or create the person, then create an Opportunity at stage "new". Give its key create:person and create:opportunity only. It runs on the server, so CORS isn't needed. Everything else can wait until the outreach pipeline runs again.
