H0 amendment A1 draft r5: agents propose CRM setup changes

2026-09-26 · scope: H0 contract, I1 authority, I3/I4/I12 consumers · base: wip/i1-authority 4cb4671 · status: DRAFT r5 for root, Fable and Opus review. Nothing is built from this until all three approve the same hash.

Your calls

  • Propose-only at launch. Recommended yes. Agents suggest; an admin approves each change. Only you (the owner) can give an agent this ability. Letting an agent change setup without asking would be a later amendment and reopens the I1 checks.
  • Default limits on that ability: recommended 10 changes per proposal and 3 open proposals per agent. You set them per agent when granting; these are only the pre-filled values.
  • Two small changes to what people can do today. (1) A field that points at one related record (a lookup) will be refused when it can get no index slot, because without one its "related records" view does not work. Other field types keep today's behavior: created without an index, they store and show values but cannot be sorted or filtered. (2) The fields that come built into the standard objects (Company, Person, Opportunity, Task and so on) can no longer be retired, because the Today feed and the won-to-delivery handoff read them. Fields you add yourself stay retirable. Recommended yes to both.

Why

Remold's promise is that the CRM reshapes to fit the business. This lets an agent suggest setup changes through the propose-then-approve path it already uses for records, and it makes every setup change leave an attributed event.

The rule

An agent with a setup.propose grant submits a proposal: a short, immutable list of additive metadata operations plus a reason. An admin reviews and approves or dismisses it. Approval runs every op through the same internal functions the human setup mutations use, with the admin as principal, in one mutation: all ops apply or none do. Nothing is deleted and no record value changes.

Shapes (additive only)

// packages/contracts/authority.ts
capability: add 'setup.propose'
capabilityScope: add
  { kind: 'setup', objects: 'new' | Id<'objects'>[], maxOps: number, maxOpen: number }
  // 'new' = may propose new objects and fields on them; ids = field ops on those objects
  // maxOps, maxOpen: safe integers >= 1, checked in issue()

SetupOp =
  | { op: 'object.create', key, label, labelPlural, icon? }
  | { op: 'field.create', object: { id: Id<'objects'> } | { ref: number },   // ref = index of an
      key, label, type, options?, targetObjectId? }                    // earlier object.create
  | { op: 'field.relabel', fieldId, label }
  | { op: 'field.addOptions', fieldId, options: { id, label, color? }[] }
  | { op: 'field.retire', fieldId }
  // strings: key /^[a-z][a-zA-Z0-9]*$/ max 40; label, labelPlural, icon, option label max 80
  // no 'required' in field.create: agent-proposed fields are always optional

setupProposals (new table, index by_org_status, by_agent_status)
  orgId, agentId, grantId, authorityEpoch,   // agent epoch at propose time
  ops: SetupOp[], reason: string (max 500),
  status: 'pending' | 'applied' | 'dismissed',
  decidedBy?: Id<'users'>, decidedAt?: number
  // ops and reason are never patched after insert

setupEvents (new table, index by_org, by_object)
  orgId, objectId, fieldId?, proposalId?,
  actor: { kind: 'user', id } | { kind: 'operator', id },   // approving admin, or ensureStandard
  op: SetupOp['op'] | 'field.releaseSlot',   // releaseSlot: event only, never proposable
  before: FieldMeta | ObjectMeta | null, after: FieldMeta | ObjectMeta | null,
  reason?, at
  // ObjectMeta = { key, label, labelPlural, icon? }
  // FieldMeta  = { key, label, type, options?, targetObjectId?, retired, slot?: { kind, index } }

The existing events table stays record-only. No change to the objects or fields schema.

A standard field is a field on an isStandard object whose key is in that object's entry in convex/lib/standard.ts. A person's custom field on a standard object whose key later becomes a standard key is locked too; that is accepted.

New objects and fields are permanent, as they already are for people. Retire is the only reverse, and the review card says so. Out of scope: object retire, field restore, undo, views, pipelines, formulas, automations (I9), roles, masks, grants.

Authority rules

  • Issuing the grant. Mode direct refused. Delegation refused. A 'new' scope needs an unrestricted owner. An ids scope needs a grantor who passes requireObjectAdministration on every listed object. issue() and within() get an explicit setup branch that never falls through to another kind.
  • Scope. A proposal names one live setup.propose grant. object.create and ref ops need a 'new' scope. Every other op's object, resolved by id, must be in the grant's ids list. Under a 'new' scope, field ops may only target objects created earlier in the same proposal, so only object.create and field.create by ref can appear. An object that is readable but outside the grant refuses FORBIDDEN after the read check, so an unreadable object still looks missing. maxOps and maxOpen are that grant's. An open proposal is one that is pending, has that grantId, and whose agent epoch still matches.
  • Proposing. Needs a concrete live setup.propose grant; it does not reuse canPropose, whose legacy branch admits migrated wildcard agents. Readonly refuses. Every fieldId must pass canReadField for the agent, and every object id and relation target canReadObject; anything unreadable returns exactly the error an id that does not exist returns. Op count above maxOps refuses. Open proposals at maxOpen refuse. Key uniqueness is not checked here.
  • Approving. Re-reads membership and runs, per op, the human checks: requireWriter(admin), requireObjectAdministration for field ops on existing objects, unrestrictedHuman for object create, requireObjectRead on relation targets. The agent's grant must be live and its current authorityEpoch equal the proposal's. Preconditions re-checked: key free (retired keys included), field exists and not retired, target is select, option ids absent, not a title or standard field, slot available for a lookup field.
  • When approval fails. The mutation throws, nothing changes, and the proposal stays pending. The admin sees the reason and dismisses it. There is no auto-close.
  • Exactly once. Approving or dismissing a proposal that is not pending returns its status and changes nothing.
  • No oracle. The agent sees only pending, applied or closed, with no reason. Dismissed, and pending with a dead grant or moved epoch, all show as closed. A hidden-key clash can only fail at approval, which the agent sees as closed, the same as any dismissal.
  • New objects start closed. No agent, including the proposer, gets grants on an object it proposed. The owner grants separately.
  • Masks. Proposals and setup events follow projectEvent: if any touched object or field is hidden from the reader, the whole item and its reason are hidden. A restricted admin cannot see or approve a proposal touching something hidden from them. Another agent asking for a proposal id gets NOT_FOUND.
  • Slots. Each object has 8 slots shared by text, select and lookup fields, 8 for numbers, 4 for dates and 4 for booleans; links use none. Slots are never reused, even after retire, except the operator release in seed:releaseStandardSlots. When none is left, the shared field-create internal refuses a lookup field on both paths, because a lookup without a slot breaks its related-records view. Every other type is created without a slot, as people get today: it stores and shows values but cannot be sorted or filtered. The review card simulates the ops in order, counting slots taken by earlier ops in the same proposal, shows the slots left, marks a lookup that would get none as "approval will fail", flags any other op that would land without one, and warns that retire does not free a slot.
  • Every setup write is evented. objects.create, fields.create/update/retire, approved proposals and seed:ensureStandard and seed:releaseStandardSlots (actor operator) write setupEvents. Seeding at org creation is the one exemption, named in code. ensureStandard keeps adding a standard field without a slot when none is left (lookups included, logged loudly), so a backfill never stops halfway.
  • Readonly. Propose, approve and dismiss are all refused while the workspace is readonly.

Human path changes (deliberate, go in the I1 parity map)

  • Lookup field create refuses when no slot is left. Other types unchanged.
  • Field retire refuses standard fields of standard objects.
  • Setup mutations write setup events.

Unchanged: people can still create required fields.

Rollback

Schema is additive and objects/fields are unchanged. Applied changes are ordinary objects and fields, so nothing reappears or disappears on rollback. Whether the old schema deploys over non-empty new tables is check R1. The I1 rollback floor still applies.
