Your calls

  • Pick the alert channel and account (for example a Slack incoming webhook, an email relay, or a paging service). Until you do, alerts queue up and nobody gets them. Any HTTPS webhook URL works with no code change: set REMOLD_ALERT_WEBHOOK_URL.
  • Confirm the defaults: stalled means not finished 15 minutes after its start time; REST alert window is 5 minutes. Both can be changed by env var.

Done and proven (builder only, not yet independently checked)

  • Before: the same three injected faults produced 0 notifications in 75 seconds. The facts existed (a failed scheduled row, a REST 500 metric, a long-running action) but nothing told anyone. baseline.json
  • After: a failed background function, a caught REST 500 and a stalled scheduled action each produced their own alert at a local HTTP sink. Repeat faults and repeat checks sent nothing new. Each alert sent one "resolved" notice after recovery. The sink got 6 notices in total, all with unique ids. service.json
  • The first alert arrived through the minute cron alone, with no manual trigger (11.6 s after the failure).
  • Scrubbing: no email, secret, record text, error text, URL query or auth header reached the sink. The scan checked every raw byte the sink received against 8 forbidden strings.
  • 13 of 13 unit mutants were killed (scrubbing x2, dedupe, each trigger, resolve x2, delivery x2, channel). One service mutant that forwarded the real Convex error text was caught by the scrub check with ['Synthetic background failure'].
  • Typecheck passes. App tests 80/80 (7 new). Authority tests 97/97. Release tests 19/19. Build passes.

What this does not prove

  • Delivery to the channel you choose. The only receiver so far was a local loopback sink, so the contract's "delivered alerts" check stays open, owner-gated.
  • Hosted behavior. Everything ran in a disposable local anonymous Convex on ports 3830/3831 with the sink on 3832. There were no provider accounts, no cloud deploys and only synthetic data.
  • Watching the watcher. If the alert cron itself stops, nothing reports it. That needs an outside heartbeat on the chosen channel.
  • Cron-invoked function failures. Convex does not write cron runs to _scheduled_functions, so only work started through ctx.scheduler is covered. Stuck integration effects (integrationOps leases) belong to the later I13 alert row and are not covered here.
  • Platform function logs were not inspected. The alert code writes no logs, and the REST 500 path is caught with a generic message.

How it works

A cron runs alerts:check every minute. It reads three things: scheduled functions from the last 60 minutes (at most 5000 rows), REST metric rows with status 500, and the list of open alerts. It then works out which conditions hold:

AlertOpens whenResolves when
background-error:<function>the latest finished run of that function faileda later run succeeds, or no failure is left in the 60 minute lookback
rest-500any caught 500 in the window (default: the previous 5 minutes plus the current one). The deliberate 503 migration pause is excludedthe window has no 500s
stalled:<function>scheduled work is still pending or running 15 minutes after its start timeit finishes
coveragethe scan hit its 5000-row cap, so some work went uncheckedthe scan fits again

One alert row exists per key. A notice is queued only when the key opens or resolves, which is where dedupe happens. Notices are built only from the kind, a code-defined function name, counts and a timestamp. Error text and arguments are never read into them. Delivery claims a notice for 60 seconds, POSTs JSON with the notice id, marks it delivered on a 2xx response, and retries otherwise. Plain HTTP is accepted only for loopback. With no channel set, notices wait and alerts:status shows the count. Delivery is at-least-once, so a receiver should dedupe by id. Notices are kept for 7 days.
