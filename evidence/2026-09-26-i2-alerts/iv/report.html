Defects with repro

D1 (high): the scan cap is above the platform read limit, so alerting stops silently under ordinary load. evaluate does take(SCAN_CAP) with SCAN_CAP = 5000 on _scheduled_functions. The local backend (convex 1.46.0) refuses more than 4096 reads in one function. Every REST request schedules telemetry:record, so about 68 requests per minute sustained over an hour is enough. Repro: node evidence/2026-09-26-i2-alerts/iv/scripts/alerts-attacks.mjs. Phase coverage sends 5100 GET requests, then alerts:check returns "Too many reads in a single function execution (limit: 4096)". The large-arguments phase gives the same error. Counter-check with the cap set to 3500 (attacks-cap3500.json): the read limit is gone, but under the same burst evaluate then failed on write conflicts. Its range read over _scheduled_functions and opsMetrics conflicts with every new telemetry:record. So lowering the cap alone is not enough. The scan probably needs an index on state or a smaller window, and something outside must notice when the check itself fails. I did not measure whether it recovers under steady moderate load. I also did not check whether the hosted limit is the same number.

D2 (medium): a long stall reports as resolved. The scan only covers rows created in the last 60 minutes. Repro (scripts/alerts.iv.test.ts, copy it into convex/ and run vitest): a job stays pending. At 16 min the stall opens. At 61 min a "Resolved: Scheduled function telemetry:record was stalled" notice is queued while the job is still pending. In the same way, a job scheduled 50 min ahead and 20 min overdue produces no alert.

D3 (release gap): preflight refuses this schema with the current rollback target. notes.json is class expand with target bb8e3ed. Schema digests: candidate e6b37063..., target 2077681f.... preflight throws "Rollback schema differs". This is not a code bug, but the slice cannot ship until it is fixed, and the handover does not mention it.

D4 (low): the loopback-only HTTP rule is bypassed by a redirect. Repro in attacks.json redirect phase: webhook http://127.0.0.1:3922/redirect answers 307 to http://[::1]:3923/landed. The IPv6 listener received the POST with the full notice. Setting the same [::1] URL directly is refused. Fix: redirect: "error" or "manual" on the fetch. The impact is small because the notice holds no customer data and the operator sets the URL.

D5 (low): a slow sink can double-send even with the claim. Repro in alerts.iv.test.ts: two queued notices, the first send takes 70 s, and a manual check runs meanwhile. Both ids are sent twice. Convex does not overlap runs of the same cron, so this needs a manual check or a slow batch. This is within "at least once", but it contradicts the "sends a notice once even when two checks overlap" test name and the code comment.

Test gaps (my surviving mutants)

  • Channel: 0.0.0.0 accepted; any host starting with "localhost" accepted; any non-http scheme (ftp, file) accepted. All three survive.
  • Stall measured from creation time instead of due time survives.
  • evaluate never marks the scan truncated survives (the coverage test bypasses evaluate).
  • Retention removed survives.

  • Platform function logs. Convex logs the error text of failed scheduled functions, which is outside this slice.
