Your calls

  • Rollback target. The tested rollback goes back to the expanded I1 schema and code, which is the recovery the plan names. Rolling all the way back to the pre-I1 code (3339517) after migration is not safe. That code matches grants by object key, so an object created later under a reused key could widen access again. My recommendation: forbid pre-I1 code rollback after the freeze. Confirm or overrule.
  • What stays allowed in readonly. This is what the sweep observed. Owners can still revoke agents and grants, narrow masks, cancel operations, disconnect integrations, remove members, and dismiss suggestions. Members can leave. Agents can cancel their own work. Operators can record provisional absence, and the human safety refund path still works. Everything else is refused, and the refused calls leave the data unchanged. Confirm this is the readonly you want.
  • Who verifies. I1 needs an independent verifier: a fresh session or Opus 5.5 with no builder context, using the attack list below. Name who runs it.

Attack cases for the independent verifier

This is authorized defensive testing of the owner's own application. Run it on an isolated local backend with synthetic data only. Write your own probes rather than reusing the builder's tests.

  1. Old wildcard agent writing a newly added object. Take a legacy agent with create/update/delete:* at 3339517. Freeze, then create a new object before backfill, after migrateAgent, and after a schema rollback and restore. Try REST /changes, the baseline-built MCP remold_apply_change and remold_propose_change, a proposal that a human later applies, CSV import, and the related-record paths. Also try reusing an old object key and renaming an object to a pre-freeze key.
  2. Role downgrade. An admin approves a queued operation, then is downgraded to member (or removed and re-invited) between claim and permit. A manager agent's agent.manage or parent grant is revoked, or the manager is fired, while a delegated child holds a claim. Try it at step 2 of a continuation and after a retryable failure and reclaim. The permit must be refused.
  3. Stale approval. Edit any material payload field after approval. Let the approval expire between claim and permit. Approve a fired agent's original proposal (must be refused; adoption must create a new attributed command). Replay an old fence or an old permit after a reclaim.
  4. Hidden field in an open subscription. Hold a live records.get or records.list subscription as a member, and hide a field via authority/policies:setMember. Measure how long until the value disappears (target under 2 s). Also try to infer the hidden value through sort or filter on the hidden field, search text, CSV export, duplicate detection in capture or import, event history, suggestion diffs, lookup titles and inbox links.
  5. Invalid secret reference. Register a raw credential as a handle. Connect with another org's reference. Disable the provider after connect. Change the reference's account, environment or provider. Revoke the reference while work is queued. Then grep the backend log, the export and every error body for the handle and keys.
  6. Same ID, different provider instance. Bind one externalId under different accounts, environments, provider names and orgs. Use each adapter key against the others' bindings, operations, intents and cursors across all 15 adapter endpoints. Send suppression callbacks and confirm only the owning binding's recipient changes.
  7. Readonly bypass. Set flags.readonly, then try every public mutation, agent REST POST and adapter endpoint. Anything besides the reductions and settlements listed under Your calls must be refused with no data change. Check the scheduler paths (lifecycle sweep and expiry, safety send) for new external sends.
