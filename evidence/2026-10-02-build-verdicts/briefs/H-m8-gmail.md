# Job H: M8 who replied (Gmail dates into Remold, read-only)
Branch: m8/gmail-dates. Job id: H-m8. Base: origin/integ/m3b (has the Activity object with type/when/about/source and with-time dates; agent keys with field grants; REST POST /api/v1/changes).

Goal: "last contact" on each person in Remold is true, from Shakur's Gmail, in and out, without Remold ever holding mail bodies or Gmail credentials, and without a Google OAuth app (Google classes gmail.metadata/readonly as restricted scopes, which can require a security assessment). Decision: a Google Apps Script that runs inside Shakur's own Google account on a daily trigger, reads only message headers/dates for people already in Remold, and posts Activities to Remold's REST API with a narrowly granted Remold key.

Build:
1. ops/gmail-sync/Code.gs (Apps Script, plain JS) plus ops/gmail-sync/README.md (short setup steps a person follows once: create script at script.google.com, paste, set Script Properties REMOLD_BASE_URL and REMOLD_KEY, run once to authorize, add a daily trigger). The script: (a) GETs People (email field only) from Remold REST; (b) for each email, searches Gmail for messages to/from it since a stored watermark (GmailApp.search with from:/to: and after:), reading ONLY date, direction (sent by Shakur vs received), and the Gmail message id; never subject, never body, never attachments; (c) for each new message, POSTs one Activity {title: "Email sent"|"Email received", type: email, when: ISO instant, about: person id, source: "gmail:<messageId>"} with an Idempotency-Key header equal to "gmail:<messageId>", so reruns create nothing new; (d) stores the watermark in Script Properties only after success. Keep it small.
2. Put all pure logic (query building, direction detection from the From header against the owner's own addresses, payload building, watermark handling, dedupe) in a module that both Code.gs and a node test can load (e.g. ops/gmail-sync/logic.js with a tiny export shim), and unit-test it with vitest using stubbed GmailApp/UrlFetchApp/PropertiesService objects: direction both ways; no subject/body ever read (stubs throw if getSubject/getBody/getPlainBody/getAttachments are called); rerun with the same messages posts with the same idempotency keys; watermark only advances after all posts succeed; a 4xx from Remold stops and reports.
3. Remold side: a "Gmail sync key" preset in Settings (like the website intake key if that exists on this base; otherwise use the existing key + grants UI) granting exactly: read Person email (and title), create Activity. Prove with a test that such a key cannot read other Person fields, cannot read other objects, and cannot update or delete. Reuse existing grant machinery; do not add a new auth path.
4. Person "last contact": show on the person page and in the people list the newest Activity "when" about that person (computed, no new stored field if avoidable), respecting read permissions.

Done when: unit tests above fail-before/pass-after; key-scope tests; last-contact test (newest of several activities, hidden when the activity is unreadable); full suites pass (use --maxWorkers=2 --testTimeout=15000); handover includes the exact setup steps and states plainly that installing the script and authorizing it needs Shakur's Google sign-in.
