# Job C: M6 a website lead lands once (Remold side)
Branch: m6/lead-intake. Job id: C-m6.

Context: read docs/unified-launch/remaining-work-2026-10-01.html section M6, docs/spec/replace-baserow.html, docs/adr/002-events.md (idempotency design), convex/http.ts, convex/agentApi.ts (REST incl. POST /api/v1/changes), convex/identity.ts (grants; note old-style create:x grants skip the field check), convex/rateLimit.ts, src/components/AgentsCard.tsx (how keys and grants are made), convex/lib/find.ts. The website (a separate repo, not yours) already emails each lead to Shakur and will call Remold after the email is sent; Remold being down must never block that email.

Build:
1. Idempotency-Key on POST /api/v1/changes as designed in ADR 002: same key + same body returns the original result without a second write; same key + different body is refused (409/422 per the ADR); concurrent duplicates produce one write. Keys are scoped per agent key and expire after a documented window.
2. One intake call: POST /api/v1/intake/lead with { name, email, phone?, company?, message?, source?, campaign? } plus required Idempotency-Key. In one mutation (all or nothing): normalize email (trim, lowercase) and phone (digits, keep leading +); find the Person by normalized email, else by normalized phone, else create; never overwrite existing non-empty Person fields; create one Opportunity at stage "new" linked to the Person (and Company if given, find-or-create by title); attach the message as a Note about the Opportunity; record the source. If both email and phone match different people, do not merge: create the Opportunity on the email match and flag the conflict in the note. Every write goes through applyChange with attributed events.
3. Least-privilege intake key: a key that can call the intake endpoint and nothing else: no reads, no other writes. Use the new-style field grants (not create:x); make it creatable from Settings as "Website intake key". Tests: that key gets 403 on GET records and on /changes; a normal key cannot call intake unless granted.
4. Abuse limits: rate limit per key and per normalized email (reuse rateLimit.ts), a cap on leads created per day per workspace (env REMOLD_INTAKE_DAILY_CAP, default 50), and when a limit trips, an operator alert through the existing alerts path. Over-limit returns 429 and writes nothing.

Done when: tests prove: same lead twice with the same key gives one Person + one Opportunity; two concurrent identical calls give one; same key different body refused; "Shakur@X.com " and "shakur@x.com" reach the same Person; a failure mid-way leaves no partial records; the intake key cannot read; a burst hits the limit; removing the idempotency check makes a test fail. Full suites pass. Handover includes the exact request/response contract (curl example with placeholder key) the website will use.
