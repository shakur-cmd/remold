2026-09-24 · Independent reviewer /root/c0_verifier · SERVICE capability and transport; SIM receiver

Corrected conclusion

The HTTP payload does carry a useful scoped credential. Absence of an Authorization header does not mean absence of a bearer token. The body contains a connection-intents capability. The tested capability enforces company, task and live-run boundaries. This does not prove executor operating-system isolation or select Paperclip.

Done and proven

A fresh, real task-bound heartbeat delivered the token to the local trusted receiver. While that request was open, the token successfully used MCP and searched synthetic connector metadata in A. After HTTP 202, the run became succeeded and the same token was denied. The independent probe exited 0. No token values, real credentials, raw request bodies or provider responses appear in evidence.

Source assessment

Exact commit remains e006c18f2036d95d47ca8f7eb068670f3c54942d. Token construction and verification bind company, agent, run, responsible user, instance, scope and expiration with HMAC. The connection-intents token has a one-hour TTL. A separate GitHub-credentials scope exists and was not exercised.

Runtime routes validate before MCP initialization, tool listing and calls. Run-context validation requires the bound running heartbeat, current responsible identity/membership, a task in the same company, current assignee ownership and an open task. Search inventory uses the bound company and checks configured connection grants before exposing indexed metadata. The runtime tools are connection discovery and connection requests, not general access to every connector’s executable tools.

Practical implication

The earlier claim that HTTP forwards no credential is incorrect. A trusted remote receiver can use the narrow capability while the task-bound HTTP call remains active. Returning 202 ends this demonstrated capability window because Paperclip treats the response as success. This is not a demonstrated asynchronous completion protocol; longer-lived job callbacks, fencing, crash recovery and outcome reconciliation remain separate proof requirements. Holding HTTP open could retain the run temporarily, but its lifecycle and failure handling have not been certified.

Fixture and limits

Container remold-paperclip-proof-http uses the same pinned prepared image/volume with the private receiver origin allowlisted at 127.0.0.1:3555. The receiver and server share a container. This proves transport and API capability behavior only. The fixture created disabled draft A/B connections with no credentials, using inert endpoint metadata; it did not enable them, call connector tools, authorize an account or send any external message. A disabled same-company request is deliberately rejected before it could create a user connection request.

Live search, disabled-request rejection, foreign lookup denial, tampered signature and ended-run denial were exercised. Live membership removal, reassignment, token expiration after one hour, GitHub capability, tool-grant variations, every MCP method, task-bridge writes, actual provider tools and hostile remote executor isolation were not exercised. These are not implicitly accepted.
